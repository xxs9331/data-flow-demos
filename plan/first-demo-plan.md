# 数据链路 Demo 库与首篇博客

## 目标

建立可持续扩充的 GitHub 仓库。先看数据链路，再看处理实现；每个独立 demo 至少对应一篇博客和一个真实案例。首篇连同代码打包为可直接打开的文书项目，由作者审查。

## 范围

- 输入：追更阅读器当前工作区中的未读状态计算、对应回归案例；全部运行样例使用合成数据。
- 输出：数据地图、单文件 demo、测试、中文博客、真实案例及源码出处、贡献模板、关系检查、文书项目打包入口和首份审查包。
- 约束：demo 只依赖 Node 标准库，复制一个文件即可运行；处理函数、样例和命令入口放在同一文件。博客在仓库中标为待作者审查；GitHub 仓库作为公开资料源，提供目录索引和按提交读取约定。
- 保留原阅读器和文书应用工作区，不修改其业务源码、用户数据或审核记录。不发布到博客平台，不调用模型，不生成虚假的插件或桌面验收结果。

## 验收标准

1. 从首页可沿数据地图找到博客、demo 和真实案例，三者均可返回其余入口。
2. demo 单文件在仓库内及复制到临时目录后均能运行；回归验证覆盖过期、重领、完成、起点、跨书隔离和输入不变。
3. 原始错误判定在重现案例中仍产生错误结果；修正后的 demo 与留存的真实源码选段一致。
4. 全部登记的 demo 都有博客、案例、运行入口和真实函数绑定；相对文件链接有效。
5. 文书项目包含持久化修改目标、博客主稿、可读取的代码参考资料和原始附件。使用文书实际项目读取逻辑打开；搬移后仍可打开，打包不调用模型。
6. GitHub 首次推送读回提交及公开可见性；确认匿名读取索引、博客和代码；自动检查结果以真实运行记录为准。

## 执行批次

### 批次一：链路与合同

目标：确定“书籍完成状态＋领取记录＋时间 → 有效未读记录 → 展示状态”的数据合同及仓库入口。

输入 / 输出：真实源码、用户习惯 → 数据地图、JSDoc 类型、函数定义与本计划。

验收标准：数据位置明确，处理节点绑定真实源码，明确排除领取调度和整个界面。

状态：已审阅合同；沿用用户“把框架搭好，把第一个 demo 搭好”的实现授权，继续实现。

### 批次二：实现、博客与交付

目标：实现单文件 demo、独立回归、博客及原始案例，建立扩充规则，生成首次文书审查包并推送公开仓库。文书侧 GitHub 接入由作者另行安排。

输入 / 输出：批次一合同 → 可运行仓库、验证结果、文书项目。

验收标准：以上六项标准。

状态：已完成。独立运行、九项回归、源码选段对照、文书项目读取及搬移、GitHub 推送与线上检查均已验证。具体证据与验证范围见 [交付验证](../docs/verification.md)。
